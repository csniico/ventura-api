# Postgres / MikroORM User Datasource — Progress Notes

## Goal
Migrate the user module's storage from MongoDB (Mongoose) to PostgreSQL (MikroORM v7). The new stack lives under `src/user/{domain,infrastructure,application}` and is exposed through `UserRepository` / `USER_DATA_SOURCE` (see `src/user/domain/user.repository.ts`, `src/user/user.module.ts`). The legacy Mongoose stack (`src/user/user.service.ts`, `src/user/user.controller.ts`, `src/user/schemas/*`) still runs in parallel and is the parity reference.

## Done
1. `src/user/domain/postgres.user-entity.ts` — MikroORM v7 `defineEntity()` schema builder. v7 removed the decorator API (`@Entity`/`@PrimaryKey`/`@Property`) from `@mikro-orm/core`; `defineEntity()` is the replacement. Current columns: `id` (uuid pk, `defaultRaw('gen_random_uuid()')`), `shortId` (`onCreate(() => nanoid(6))`), `role` (enum, defaults `UserRole.OWNER`), `firstName`, `lastName?`, `email` (unique), `googleId?`, `appleId?`, `password?`, `avatar?` (`json<ImageResource>`), `businessId?`. Nullable columns use `.nullable()`. Exports `PostgresUser = InferEntity<typeof PostgresUserEntity>` for typing.
   - Property names match `IUser` (`src/user/domain/user.entity.ts`) exactly, including `firstName`.
2. `src/user/infrastructure/postgres-user.repository.ts`:
   - `@Injectable()` is required — without it, Nest can't read constructor DI metadata and silently fails to inject `EntityManager`.
   - `toDomain()` maps MikroORM's `null` → `undefined` so persistence nullability doesn't leak into the `IUser` domain contract (repository pattern boundary).
3. `src/app.module.ts` — `MikroOrmModule.forRootAsync` requires `driver: PostgreSqlDriver` as a **top-level** option, not only inside the `useFactory` return value. Without it, `@mikro-orm/nestjs` can't pre-resolve the concrete `PostgreSqlEntityManager` DI token before the factory runs, so nothing in the app can inject it (`UnknownDependenciesException`).
4. `mikro-orm.config.ts` (repo root) — standalone config consumed only by the MikroORM CLI (migrations), not by the running app. Mirrors the Postgres connection settings in `app.module.ts` manually (the CLI runs outside Nest's `ConfigService`, so it loads env vars directly via `dotenv/config`). Keep the two in sync by hand when connection settings change.
5. Installed `@mikro-orm/migrations`, `@mikro-orm/cli`, and `tsx`. `tsx` is required — MikroORM CLI v7 needs one of `tsx`/`@swc-node/register`+`@swc/core`/`oxc`/`jiti`/`tsimp` to load `.ts` config files; plain `ts-node` (already a devDependency) is not sufficient.
6. Added `package.json` scripts: `migration:create`, `migration:up`, `migration:down`.
7. **Migrations generated and applied.** The `users` table now exists in Postgres — `POST /v2/users/email` (`createEmailUser`) persists successfully. New entities/columns still require a new migration (`pnpm run migration:create` → `pnpm run migration:up`).

## Tests
- `src/user/application/user.service.v2.spec.ts` mirrors all 42 scenarios of the legacy `user.service.spec.ts` against `UserServiceV2`, exercised through in-memory fakes of the repository ports (`UserRepository` / `EmailChangeRepository`). Runs under the existing CJS Jest and passes (42/42). The real `PostgresUserRepository` SQL path is covered by the live smoke test.
- **Why not a direct swap of the Mongo integration spec:** that spec is a MongoDB integration test — it injects the Mongoose model and verifies writes through it, and uses ObjectId `_id`s. `UserServiceV2` writes to Postgres via injected repositories, so it can't bind to that spec unchanged. Additionally, MikroORM v7 is **ESM-only** and this repo's Jest is CommonJS (ts-jest); importing `@mikro-orm/*` in a spec fails to parse (hits `import.meta`), so a MikroORM-backed integration spec needs a full Jest-ESM migration (not done — would touch all suites). The fake-repository spec sidesteps both issues while proving behavioural parity.
- One intentional output delta vs legacy: v2's `UserResponse` returns `null` for absent optional fields (e.g. `googleId`) where the Mongoose doc returned `undefined`; `_id` is a uuid, not an ObjectId.

## App-wide migration plan (agreed 2026-07-25)
Decisions:
- **Tenancy model = shared schema + `businessId` discriminator**, NOT schema-per-tenant. The existing `src/common/middleware/tenant.middleware.ts` (which forks the EM per `tenant_<id>` schema) is therefore **superseded** — it should be reworked/removed, and registration does NOT provision per-tenant schemas. Tenant-scoped tables keep a `businessId` column; scope reads with MikroORM global filters (or explicit `businessId` in every query). All tables live in `public`.
- **Scope for now = finalize the user module only.** Do not migrate other modules' storage yet.

Critical constraint discovered — **repointing user consumers is all-or-nothing.** 8 modules call `userService.getUserById(req.user.userId)` where `req.user.userId` is the JWT `sub`. The moment `auth` issues tokens from Postgres users (uuid `sub`), every `getUserById` consumer must also read from Postgres, or it 404s/CastErrors against Mongo. So you cannot repoint just auth/admin/business/setup — you repoint all 11 consumers (auth, admin, business, setup, customer, order, invoice, appointment, dashboard, resource, search) together, or none. Consumers: 8 use only `getUserById`; `auth` uses the full auth-support surface (already in v2) and must switch `String(user._id)` → `user.id`; `business` uses `setBusinessId`; `admin.manage-users.service` additionally has its OWN direct Mongo user queries (`listUsers`, `hardDeleteUser`) that need new repo methods (`list`, `hardDelete`) before it can move.

Per-module migration recipe (proven on `user`): `defineEntity` → repository interface + Postgres impl → service (business logic, DIP) → controller → module wiring → migration → tests (fake-repo unit spec + live smoke). Testing caveat: MikroORM v7 is ESM-only and Jest here is CJS, so real ORM integration specs need a Jest→ESM migration; default to fake-repo unit specs + smoke instead.

Next concrete step when ready to cut the app over to Postgres users: add `UserRepository.list()` + `hardDelete()`, then repoint all 11 consumers to `UserServiceV2` in one change (auth `_id`→`id`), wire nothing tenant-schema-related, and delete the legacy Mongoose user stack.
